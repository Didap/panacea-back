# RLS isolation test - 2026-06-05

Closes the gap flagged when CI landed: the RLS policies in `0002_rls.sql` / `0004_rls_delegations.sql`
were applied by migrations but never exercised (v0 services use the BYPASSRLS admin pool, and the
e2e seeds via an admin connection). CI proved migrations apply, not that the tenancy boundary holds.

## What the test does

`test/rls.e2e-spec.ts` drives the real production RLS path: `DatabaseService.withUser(userId, fn)`
opens a transaction on the `panacea_app` pool and sets `app.current_user_id` transaction-locally.
Seeding is done via `db.admin()` (BYPASSRLS); every assertion runs through the app role.

- A patient sees only their own `health_documents`, never another patient's.
- `db.app()` with no actor set sees nothing - proves RLS is enforced, not bypassed (this is the
  anti-false-green guard).
- An active delegation (delegator -> delegate) widens the delegate's access to the delegator's
  documents; flipping the delegation to `revoked` closes it immediately. Exercises the
  `health_documents_owner_or_delegate` policy from `0004`.
- The policy `WITH CHECK` rejects an `INSERT` of a document owned by someone you hold no active
  delegation from.

## Teeth (mutation check)

Verified the test is not tautological: with `ALTER TABLE health_documents DISABLE ROW LEVEL SECURITY`
all 4 tests fail; re-enabling RLS makes them pass again. So a future regression that weakens or drops
the policy turns CI red.

## Verification

`npm run test:e2e` -> 3 suites, 8 tests green (health + delegations + rls). typecheck and lint clean.
The CI e2e step runs this spec automatically (testRegex `.e2e-spec.ts$`).
